## 1. [P1-1] 예약 시간 충돌 검증 API

### 배경
- 현재 같은 직원에게 같은 시간대에 예약 2건 등록이 가능
- 매장 관리자가 수동으로 확인해야 하며, 실 운영 시 더블부킹 사고 발생 가능

### 요청 사항

#### API 1: 직원 가용 시간 확인
```
GET /api/businesses/{businessId}/reservations/availability
```

**Query Parameters:**
| 파라미터 | 타입 | 필수 | 설명 |
|---------|------|------|------|
| staffId | Long | Y | 직원 ID |
| date | String (YYYY-MM-DD) | Y | 예약 날짜 |
| startTime | String (HH:mm) | Y | 시작 시간 |
| endTime | String (HH:mm) | Y | 종료 시간 |
| excludeReservationId | Long | N | 수정 시 현재 예약 제외 |

**Response (200):**
```json
{
  "available": true,
  "conflicts": []
}
```

**Response (200, 충돌 시):**
```json
{
  "available": false,
  "conflicts": [
    {
      "reservationId": 123,
      "customerName": "홍길동",
      "startTime": "14:00",
      "endTime": "15:00",
      "serviceName": "커트"
    }
  ]
}
```

#### API 2: 예약 생성/수정 시 서버 측 검증
- 기존 `POST /api/businesses/{businessId}/reservations` 에 시간 충돌 검증 로직 추가
- 기존 `PUT /api/businesses/{businessId}/reservations/{id}` 에도 동일 적용
- 충돌 발생 시 에러 응답:

```json
{
  "code": "RV006",
  "message": "해당 시간에 이미 예약이 있습니다",
  "conflicts": [...]
}
```

### 프론트엔드 연동 계획
- FE에서 시간 선택 후 availability API 호출 → 충돌 시 경고 표시
- 서버 측에서도 이중으로 검증 (race condition 방지)

## 2. [P2-2] 다중 예약 일괄 상태 변경 API

### 배경
- 현재 예약 1건씩만 상태 변경 가능
- 매장 관리자가 여러 예약을 한 번에 "확정" 또는 "완료" 처리 필요

### 요청 사항

```
PATCH /api/businesses/{businessId}/reservations/bulk-status
```

**Request Body:**
```json
{
  "reservationIds": [1, 2, 3, 5],
  "status": "CONFIRMED"
}
```

**허용 상태 전이:**
- PENDING → CONFIRMED (일괄 확정)
- CONFIRMED → COMPLETED (일괄 완료)
- PENDING/CONFIRMED → CANCELLED (일괄 취소)

**Response (200):**
```json
{
  "success": [1, 2, 3],
  "failed": [
    {
      "reservationId": 5,
      "reason": "이미 취소된 예약입니다"
    }
  ]
}
```

### 프론트엔드 연동 계획
- 예약 목록에 체크박스 추가
- 선택 후 상단에 "일괄 확정" / "일괄 완료" 액션 버튼 표시

## 3. [P2-4] 재예약용 이전 예약 조회 API

### 배경
- 재방문 고객이 이전과 동일한 서비스/스태프로 재예약하려면 매번 다시 선택해야 함
- "같은 서비스로 재예약" 기능으로 이전 예약 정보 자동 채움

### 요청 사항

기존 API에서 이미 예약 상세 조회가 가능한 경우, 추가 API 불필요할 수 있습니다.

**확인 필요:**
```
GET /api/businesses/{businessId}/reservations/{id}
```
위 응답에 `services`, `staffId`, `staffName` 정보가 포함되는지 확인 필요.

**만약 고객용 API가 필요하다면:**
```
GET /api/customer/reservations/{id}
```
- 고객 토큰으로 인증
- 이전 예약의 서비스 목록, 스태프, 매장 slug 정보 반환

### 프론트엔드 연동 계획
- 내 예약 목록에서 "재예약" 버튼 클릭
- 이전 예약 정보 조회 → 예약 페이지로 이동 시 서비스/스태프 자동 선택

## 4. [P2-7] 서비스 이름 중복 검증 API

### 배경
- 현재 같은 매장 내에서 동일한 이름의 서비스를 중복 등록 가능
- 관리 혼란 발생 가능

### 요청 사항

#### 방법 A: 기존 생성/수정 API에 검증 추가 (권장)
- `POST /api/businesses/{businessId}/services` 에서 동일 이름 존재 시:
- `PUT /api/businesses/{businessId}/services/{id}` 에서 동일 이름 존재 시:

```json
{
  "code": "SV006",
  "message": "동일한 이름의 서비스가 이미 존재합니다"
}
```

#### 방법 B: 별도 중복 확인 API (선택)
```
GET /api/businesses/{businessId}/services/check-name?name=커트&excludeId=5
```

**Response:**
```json
{
  "duplicate": false
}
```

### 프론트엔드 연동 계획
- 서비스 폼에서 이름 입력 시 실시간 중복 체크 (debounce 300ms)
- 또는 저장 시 서버 에러 코드로 안내

## 5. [P2-8] VIP/단골 임계값 설정 API

### 배경
- 현재 VIP/단골 판정 기준이 하드코딩 또는 고정값
- 매장별로 "3회 이상 방문 = 단골", "10회 이상 = VIP" 등 커스텀 필요

### 요청 사항

#### 설정 저장
```
PUT /api/businesses/{businessId}/settings/customer-tiers
```

**Request Body:**
```json
{
  "regularThreshold": 3,
  "vipThreshold": 10,
  "vipBenefitDescription": "VIP 고객 10% 할인"
}
```

#### 설정 조회
```
GET /api/businesses/{businessId}/settings/customer-tiers
```

**Response (200):**
```json
{
  "regularThreshold": 3,
  "vipThreshold": 10,
  "vipBenefitDescription": "VIP 고객 10% 할인"
}
```

**기본값 (설정 미존재 시):**
```json
{
  "regularThreshold": 3,
  "vipThreshold": 10,
  "vipBenefitDescription": ""
}
```

### 프론트엔드 연동 계획
- 매장 설정 페이지에 "고객 등급 기준" 섹션 추가
- 임계값 입력 → 저장 → 고객 목록에 반영

## 참고: 에러 코드 체계

기존 프로젝트 에러 코드 패턴을 따릅니다:

| 접두사 | 도메인 | 기존 코드 |
|--------|--------|----------|
| CP | 고객 프로필 | CP001~CP004 |
| SV | 서비스 | SV004~SV005 |
| RV | 예약 | (신규: RV006) |

**신규 에러 코드 제안:**
- `RV006`: 예약 시간 충돌
- `SV006`: 서비스 이름 중복
- `BS001`: 일괄 처리 부분 실패
